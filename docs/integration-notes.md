## 3. Data Type & Schema Ambiguities

The following 8 contract ambiguities risk runtime Pydantic validation errors (HTTP 422/500) if not explicitly standardized across modules:

### 1. Confidence & Risk Score Scales (`0.0 - 1.0` vs `0 - 100`)
- **Fields**: `confidence` (Modules 2 & 4), `risk_score` (Module 4), `urgency_score` (Module 2), `origin_risk.score` (Module 3).
- **Issue**: Protocol forensics enforces `score: float = Field(ge=0.0, le=1.0)`. Other models define unconstrained `float`. If an ML model returns a percentage integer (e.g. `85` or `85.0`) instead of `0.85`, downstream risk scoring will compute invalid values `> 1.0`.
- **Standard**: All risk scores and confidence values must be normalized floats in the range `[0.0, 1.0]`.

### 2. Timestamp Format Discrepancies (`ISO 8601` vs `Unix Epoch` vs `Raw WHOIS`)
- **Fields**: `domain_intel.registered_at` and `domain_intel.creation_timestamp` (Module 3).
- **Issue**: Both fields are typed as `str | None`. Python's `python-whois` often returns raw strings (e.g., `"15-Jan-2023 12:00:00"`), `datetime` objects, or a list of datetimes. Additionally, having two separate fields for creation date creates duplication.
- **Standard**: Normalize both fields to ISO 8601 UTC strings (`"YYYY-MM-DDTHH:MM:SSZ"`), or consolidate to `registered_at`.

### 3. ASN Data Type Coercion (`int` vs `str`)
- **Field**: `sender_ip.network.asn` (Module 3).
- **Issue**: Schema defines `asn: int = 0`. Many WHOIS/RDAP services return ASNs with prefix strings like `"AS15169"`. Passing `"AS15169"` to Pydantic raises a `ValidationError`.
- **Standard**: The origin module must strip non-digit prefixes and return a clean integer (e.g., `15169`).

### 4. Classifier Prediction Label Restriction
- **Fields**: `label` in `ClassifierOutput` and `ClassifierBaseline`.
- **Issue**: Strictly typed as `Literal["phishing", "legitimate"]`. If the ML classifier outputs `"suspicious"`, `"unknown"`, or `"inconclusive"`, Pydantic will reject the payload.
- **Standard**: Either mandate binary decision output (`"phishing"` or `"legitimate"`), or expand the literal definition in `schemas.py` to include `"suspicious"` and `"unknown"`.

### 5. Country Code Formatting (`Alpha-2` vs Full Name)
- **Fields**: `sender_ip.country` and `sender_ip.network.country`.
- **Issue**: MaxMind provides both two-letter codes (e.g., `"US"`) and full country names (`"United States"`).
- **Standard**: Standardize on uppercase ISO 3166-1 alpha-2 codes (`"US"`, `"IN"`, `"DE"`).

### 6. Weight Normalization in Fusion Engine
- **Field**: `weights: dict[str, float]` (Module 4).
- **Issue**: Contract does not specify whether weights must sum to `1.0` (e.g., `0.35 + 0.35 + 0.30 = 1.0`) or if arbitrary ratios (e.g. `35, 35, 30`) are accepted and normalized.
- **Standard**: Require weights to be pre-normalized floats summing strictly to `1.0`.

### 7. Shared Signals Representation in Campaigns
- **Field**: `shared_signals: list[str]` in `CampaignSummary` and `CorrelationCandidate`.
- **Issue**: Format is unspecified (could be free-text sentences or structured identifiers).
- **Standard**: Adopt machine-readable tagged strings: `["ip:198.51.100.10", "domain:bank.example", "subject_hash:a3f12b"]`.

### 8. HTML Ratio Measurement Scale
- **Field**: `content_features.html_ratio` (Module 2).
- **Issue**: Ambiguous whether this measures tag-to-body byte ratio, HTML tag count, or a percentage `[0, 100]`.
- **Standard**: Float in range `[0.0, 1.0]` representing `len(html_tags) / len(raw_body)`.
